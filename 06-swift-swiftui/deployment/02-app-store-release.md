## 🎯 本指南解决什么问题

上架被拒的三大来源：**元数据不全**、**权限描述与行为不符**、**审核员无法完成关键路径**。本指南按"准备 → 提审 → 应对审核 → 版本迭代"四步给出可勾选的执行清单。

## 🛠️ 任务一：创建 App 记录与基础信息

1. App Store Connect → 我的 App → ➕ → **新建 App**
2. 填写四项：名称（全球唯一）、主要语言（简体中文）、Bundle ID（选择已注册的）、SKU（内部识别码，如 `habittracker-2026`）
3. 确认价格、税务类别和上架地区；默认地区与可选地区以 App Store Connect 当前界面为准，先在目标地区小范围验证运营与支持流程再扩大。

## 🛠️ 任务二：准备元数据与截图

### 截图（决定下载率的第一要素）

| 设备尺寸 | 数量要求 | 建议 |
|----------|---------|------|
| 6.9 英寸（iPhone） | 必传 | 主打功能放第 1 张 |
| 6.5 英寸（iPhone） | 视最低部署版本 | 可用工具从 6.9 缩放 |
| 12.9 英寸（iPad） | App 支持 iPad 则必传 | 展示宽屏布局 |

实操：模拟器 Cmd+S 截图 → 用 Xcode 自带或第三方工具加边框与文案；前 3 张截图决定转化，依次放"核心价值 → 主要功能 → 差异化亮点"。

### 文案清单

- **副标题**（30 字符）：一句话定位，如「连续打卡，习惯可视化」
- **关键词**（100 字符）：逗号分隔，勿重复 App 名称里的词
- **描述**：首段三行是摘要折叠区，前两行必须说清"是什么 + 为谁"
- **新功能**：写人话版本日志，别写"修复若干 bug"草稿式文案

### 隐私与合规（最容易卡审核的部分）

1. **隐私政策 URL** 必填——自建静态页即可，说明收集哪些数据、如何使用
2. **隐私营养标签**：在 App 隐私部分逐项声明（如"位置信息 - 用于功能实现 - 不用于追踪"），必须与真实行为一致
3. 权限描述文案逐条复查：定位、相机等每个 `NSxxxUsageDescription` 都要说清场景

## 🛠️ 任务三：提交审核

```text
1. App Store 页签 → 版本或平台 → iOS
2. 构建版本：选择已上传的 Build（TestFlight 同源）
3. 完成所有必填元数据与截图
4. 分级问卷：如实回答暴力/赌博/医疗内容等问题
5. 年龄分级生成后 → 提交以供审核
```

**提审前自检（按拒审率排序）**：

- [ ] 审核员能完成核心路径：需要登录时在 App Review Information 提供可用的演示账号、密码、测试数据和特殊操作说明；不需要登录的路径也要可直接进入，不能留“敬请期待”死页面
- [ ] 所有权限申请都在用户触发对应功能时才弹出
- [ ] 先按实际销售内容、店面地区和已获 entitlement 判断支付方案：解锁 App 内数字功能通常适用 IAP；实体商品／线下服务、美国店面或特定地区的替代支付规则可能不同。提交前逐项核对当前 [App Review Guidelines 3.1](https://developer.apple.com/app-store/review/guidelines/) 与适用 entitlement，不能用一条通用文案代替合规判断
- [ ] App 与元数据里没有"Beta/测试版"字样
- [ ] 演示账号（若 App 需登录）已填入审核信息栏

## 🛠️ 任务四：应对审核结果

### 被拒了怎么办

1. 细读 Resolution Center 的拒审理由与引用条款（通常是 Guideline 2.1 完整性、5.1.1 权限、5.1.2 数据使用）
2. 两种回应路径：**修复后重新提审**（多数情况）；**申诉**（认为误判时，附证据说明）
3. 沟通用英文简明扼要，附复现步骤视频往往比文字有效

### 过审后的发布选项

| 方式 | 行为 | 适用 |
|------|------|------|
| 手动发布 | 过审后你按按钮才上线 | 配合营销节奏 |
| 自动发布 | 过审即上线 | 常规迭代 |
| 定时发布 | 到指定日期自动上线 | 计划性大版本 |

## 🛠️ 任务五：版本迭代节奏

- 崩溃率、受影响用户数和关键旅程失败率超过团队事先约定的发布阈值时，先修复再上新功能；阈值要按产品风险和基线定义，不能把任意百分比当作 App Store 规则。用 [03-ci-cd-observability.md](./03-ci-cd-observability.md) 的监控数据决策
- 元数据更新（截图/文案）不需要重新审核代码，可与版本迭代解耦
- 保留每个上架版本的分支 tag，热修复时能快速定位历史代码

## ✅ 最佳实践

提审前验证干净安装与从旧版本升级两条路径：前者暴露未配置权限和首次启动问题，后者暴露数据迁移与登录恢复问题。无需为了测试重置用户真实设备，可使用隔离测试设备或模拟器环境。

截图、说明和隐私申报应反映实际产物；选择手动或自动发布取决于协调需求。审批通过不意味着已安装用户可以撤回到旧版，因此提前准备暂停分发和修复版流程。

## ❌ 避免陷阱

- ❌ 用私有 API 或绕过系统行为——静态扫描直接拒绝
- ❌ 权限标签声明"不收集"但 SDK 在传数据——上架后被下架风险更高
- ❌ 审核备注留空——有特殊操作（如隐藏入口）必须在备注里说清并给演示路径

## ❓ 常见问题

**Q1: 审核要多久？** 没有对每次提交的固定承诺；Apple 说明会尽快审查，复杂或有新问题的应用可能需要更多时间。以 App Store Connect 的实时状态为准，并为发布计划预留修复和重新提审时间。[Apple 的 App Review 页面](https://developer.apple.com/app-store/review/) 会公布当前平均处理信息与状态说明。

**Q2: 能否撤回审核？** 可以，审核中状态可从 App Store Connect 撤回；过审后未发布也能撤回修改。

**Q3: 加急审核怎么申请？** 开发者门户提交加急请求，理由写崩溃等用户影响类问题，滥用会失效。

## 🎯 练习

- [ ] 为习惯追踪器补齐目标设备的元数据和截图；逐项对照当前 App Store Connect 的必填项，保存提交前页面截图
- [ ] 用全新模拟器走一遍首次启动，列出所有权限弹窗时机；**期望结果**是每次请求紧跟用户触发的功能，隐私标签和权限说明能对应实际网络与 SDK 行为
- [ ] 写一份“被拒应对预案”：针对产品实际功能列出三条可能相关的审核条款、复现步骤、演示账号和修复负责人；**期望结果**是审核员无需猜测即可走到受保护的核心路径
