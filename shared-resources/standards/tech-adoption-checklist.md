# 框架与技术收录：价值、前沿性与知识寿命

知识库既要覆盖基础，也要帮助学习者识别值得投入的新能力。不能承诺框架永远不过时；应尽量让原理、问题分析和取舍在 API 变化后仍然有用。

## 三种收录深度

| 层级 | 何时采用 | 文档要求 |
|---|---|---|
| 核心学习 | 能解决本模块常见问题，具备可核查的维护与兼容支持 | 连贯教程、必要参考、可验证项目、升级边界 |
| 专题扩展 | 有明显独特价值或正在形成稳定实践，但并非人人必需 | 使用前提、与主线比较、小实验、适用与不适用场景 |
| 观察条目 | 前沿、API 易变或证据不足 | 问题定义、官方来源、实验状态、暂不进入必修路径的原因 |

存在竞争者不自动否决一个框架，发布日期新也不自动加分。没有近期发布可能是成熟稳定，也可能是停止维护，要结合支持政策、问题处理和兼容性证据判断。

## 收录前回答六个问题

1. **解决什么问题？** 给出不用它时遇到的具体困难，以及最小替代方案。
2. **谁需要？** 是所有学习者都会遇到，还是某类平台、规模或组织才需要？
3. **哪些知识可迁移？** 例如缓存身份、依赖边界、事务与取消；哪些是该库独有 API？
4. **维护证据是什么？** 查官方发布、支持周期、迁移指南与仓库维护状态，记日期与来源。
5. **学习与迁移代价是什么？** 额外运行时、原生构建、托管服务、数据格式与退出成本都应说明。
6. **如何验证价值？** 给出同一个小任务的结果比较；性能结论需要测试条件，不只看宣传数字。

下载量与星数只能作为采用情况的辅助证据。它们不证明 API 质量、安全性或适合本项目；不同 registry 的统计也不宜直接比较。

## 每篇框架文档分开三层

稳定层解释问题与机制，例如“让缓存键涵盖影响结果的输入”。版本层说明具体 API，例如某版本的配置名称。实验层记录实际版本、命令和结果。升级时先定位变化在哪一层，而不是整篇重写或直接说全部内容仍正确。

前沿专题可以保留，但要明确实验状态及不进入初学路径的理由。把特定产品 SDK 写成通用协议，或把尚在演变的协议称为永久稳定，都不符合本标准。

## 评估记录格式

| 字段 | 内容 |
|---|---|
| 主题与层级 | 核心 / 扩展 / 观察 |
| 具体任务 | 学习者希望完成的可验证任务 |
| 适用前提 | 平台、规模、已有技能 |
| 可迁移原理 | 与框架名称无关的知识 |
| 版本与来源 | 官方 URL、查询日期、已核对事实 |
| 风险与退出方式 | 数据迁移、替代实现、兼容成本 |
| 最小练习 | 输入、输出、验收和反例 |

## 既有选择怎样维护

仓库当前以 Gin、Next.js、TanStack、React Native、Compose、SwiftUI、Laravel、Spring Boot、Hono、FastAPI、Tauri/Axum 等组织主线，这表示编辑选择，不意味着其他框架质量低或已经被淘汰。

此前基于“竞争未收敛”“半年没有发布”作出的拒绝判断应视为历史选择，重新评估时必须重新查证。替代框架可以作为对比专题，只有明确需要时才扩展成第二条完整路径，避免把学习时间分散在重复 API 上。

版本漂移可借助[基线检查工具](../tools/baseline-check/README.md)，它发现差异而不自动决定升级。新增或调整内容要同步[文档索引](../tools/document-index.md)，质量验收遵循[写作规范](./documentation-guidelines.md)。
