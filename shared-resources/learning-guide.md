# 如何用 Dev Quest 学会一项技术

适合你：会变量、条件、循环和函数，但还不能解释某个框架如何把请求、数据和界面连起来。你不需要先学完 11 个技术栈，也不需要先背完所有 API。

## 第一次打开仓库

先从[总入口](../README.md)选一个模块，打开该模块的 `LEARNING_GUIDE.md`。它先解释技术在应用中的位置，再给出练习顺序和完成标准。模块 README 保留版本信息和完整目录，查具体语法再进入 reference。

一次只建立一个能运行的练习工程，放在仓库之外，例如与 `dev-quest` 同级的 `dev-quest-labs`。每完成一步保存一次代码；不要把不同章节中的多个 `main`、不同方案的配置或者多个同名组件全拼进一个文件。

## 一篇文章怎样读

以“读取待办列表”为例，先明确输入是 HTTP 请求，输出是 JSON 或屏幕上的列表。顺着数据走一遍：请求由谁发起、谁检查错误、数据保存在哪里、最后谁展示结果。遇到陌生术语，先用[术语解释](./glossary.md)理解它在这条流程中的作用，再查具体 API。

建议每次完成一个 30–60 分钟的小闭环，时间只是安排参考：

1. **预测**：运行前写下输入和预期结果。例如新增标题为空的待办，应该显示错误而不是创建空记录。
2. **运行**：按文档注明的文件、依赖和命令复现。区分“终端退出成功”和“程序行为正确”。
3. **改变**：只改一个条件，如把正常输入改为空字符串、把存在的 ID 改成不存在的 ID。
4. **解释**：说明结果在哪个函数、状态分支或数据库约束处被决定。
5. **迁移**：关掉示例，把“待办”换成“笔记”，独立做一个同类功能。

如果只能复制代码却不能预测第四步的结果，回到较小的示例。不要靠继续读高级章节解决当前概念缺口。

## 先看懂代码块的身份

| 标记 | 你需要做什么 | 什么不能据此推断 |
|---|---|---|
| 完整示例 | 按指定文件名保存，安装声明的依赖后运行 | 能运行不代表适合生产使用 |
| 局部片段 | 放入指定已有工程，补齐文档明确列出的上下文 | 单独复制通常不能运行 |
| 反例 | 预测并观察指定失败，随后改回正确写法 | 报错不意味着环境坏了 |
| 设计草图 | 用来理解职责或数据流 | 没给出的函数、数据库和组件不会自动存在 |

旧文章中仍可能有未标注的片段。遇到 `...`、`TODO`、未定义的 `service`、`db`、`fetchUser`，先确认前文是否定义了它。没有定义就把它记录为文档缺口，不要把“补完框架全部知识”当作阅读前提。

## 卡住时按证据排查

| 现象 | 先检查 | 留下什么证据 |
|---|---|---|
| 命令不存在 | 工具是否安装、终端 PATH 是否更新 | 完整命令与版本输出 |
| 找不到模块或包 | 当前目录、依赖安装结果、文件名大小写 | 工作目录、清单和第一条错误 |
| 能编译但结果不对 | 输入、分支、状态归属、返回值 | 最小输入、实际结果、预期结果 |
| 请求一直加载 | 请求是否结束、错误是否被吞、UI 分支顺序 | 状态码、错误对象、渲染分支 |
| 换电脑无法复现 | 运行时版本、锁文件、环境变量、外部服务 | 两台电脑的差异，而非整段截图 |

不要一次升级所有依赖再尝试。先记录模块 README 的基线、自己安装的版本和当前锁文件；只改变一个变量，才知道修复是否有效。

## “学完”用行为来判断

一节课完成：能解释一个机制，能复现正常情况，能解释一个失败，能独立改出一个变体。

一个模块的入门完成：能从空工程做出小应用，包含输入、验证、状态或存储、输出；能运行一条成功测试和一条失败测试；能说明重启后哪些数据会丢失。

部署完成：在新的环境按步骤启动成功，知道如何检查健康状态、如何恢复上一版以及如何保护配置。应用出现真实用户和复杂故障后，才有条件继续评估可靠性；“生产级”这个标题本身不是证明。

用[学习进度记录](./progress/learning-progress.md)记录你的证据。文档已经写好与自己已经掌握是两种不同状态。
