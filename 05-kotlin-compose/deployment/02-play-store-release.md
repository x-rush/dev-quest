## 1️⃣ 创建应用与不可变约定

1. Play Console → **创建应用**：填应用名、默认语言、应用/游戏、免费/付费
2. **包名（applicationId）一旦发布不可更改**——发布前最后确认
3. 首次发布需完成：目标受众、内容分级、广告声明、数据安全、隐私政策 URL

## 2️⃣ 商店资料（Store Listing）

| 资产 | 要求 |
|------|------|
| 应用名称 | 30 字符内，避免堆砌关键词 |
| 简短描述 | 80 字符内，说清核心价值 |
| 完整描述 | 4000 字符内，功能+亮点+更新说明习惯 |
| 图标 | 512×512 PNG |
| 置顶大图 | 1024×500，避免小字 |
| 手机截图 | 至少 2 张，建议 4-8 张（可用 [Compose Preview](../frameworks/04-devtools.md) 配合截取） |

文案策略：第一屏截图展示"一句话价值 + 核心界面"，不要从启动页开始。

## 3️⃣ 内容分级与数据安全

**内容分级问卷**：如实勾选（暴力/成人内容/交易等），产出 IARC 分级；虚报会被下架。

**数据安全表单**（用户最敏感的环节，逐项回答）：

- 应用是否收集/共享用户数据？收集了哪些类型（位置/标识符/使用数据…）？
- 数据是否加密传输？（HTTPS 即"是"，[安全实践](../advanced-topics/security/01-security-practices.md)）
- 用户能否请求删除？

> 与代码对齐：如果 App 请求了定位（如[天气应用](../projects/02-weather-app.md)），数据安全表单必须如实声明"位置"类型。

**目标 API 要求**：Play 要求 targetSdk 满足最近政策（每年 8 月起对新提交生效），
`targetSdk = 36`（Android 16）是 2026 年的安全线；Android 17（API 37）尚在 Beta，以 Play Console 提示为准。

## 4️⃣ 分轨发布（Testing Tracks）

Play 的发布轨道由内到外：

```
内部测试 → 封闭测试 → 开放测试 → 正式版(staged rollout)
 ≤100人    ≤2000人     无上限       1% → 10% → 50% → 100%
```

推荐节奏（配合 [生产级应用](../projects/04-production-android-app.md) 路线图）：

1. **内部测试**：团队冒烟，几分钟生效，验证签名/安装
2. **封闭测试**：真实用户试用 1-2 周，收集预启动报告与评价
3. **正式版灰度**：生产轨道上传后选"分阶段发布"，从 1%/10% 起步

## 5️⃣ 预启动报告（Pre-launch Report）

每次上传 AAB，Play 自动在真机矩阵上运行应用并报告：

- 崩溃与 ANR 截屏（常见：特定厂商/语言/无障碍设置下的问题）
- 无障碍问题（对比度、内容描述缺失——与 [Compose UI 测试](../testing/02-ui-testing.md) 的语义工作互补）
- 性能提示

把它当免费的"云真机 E2E"：每次新轨道上传后先看报告再放量。

## 6️⃣ 发布与更新

- **版本发布说明**：按轨道填写，简洁列"新增/修复"
- **灰度监控**：结合 [Crashlytics 与 Vitals](03-ci-cd-observability.md) 观察崩溃率，异常即暂停 rollout（已升级用户不受影响，可发新版本修复）
- **更新审核**：通常数小时到 1-2 天；政策类应用（金融/健康）更久，预留时间
- **隐私政策 URL**：任何版本更新后仍需可访问

## 7️⃣ 常见审核拒绝与规避

| 拒绝原因 | 典型场景 | 规避方式 |
|----------|----------|----------|
| 数据安全表单与实际不符 | 请求了定位但表单未声明"位置" | 表单逐项对照 Manifest 权限与 SDK 行为 |
| 缺少可用的隐私政策 | URL 404 或与 App 功能无关 | 部署稳定托管页，随版本维护 |
| 功能描述不符 | 截图展示 App 没有的功能 | 截图全部来自真实运行界面 |
| targetSdk 低于政策线 | 提交旧 targetSdk | 跟随 Play Console 年度提示升级 |
| 权限使用不合理 | 申请精确定位却只做国家级天气 | 降级为网络定位（IP 级）并删掉权限 |
| 支付绕过 Play 计费 | 实体商品之外的数字商品用三方支付 | 数字商品走 Play Billing，实物不限 |
| 应用内容缺失元数据 | 缺内容分级/目标受众问卷未完成 | 创建应用后逐项走完 Console 必填清单 |

提交被拒时的正确动作：Console 会给出政策链接，**逐条对照修改后重新提交**，不要直接申诉
（申诉周期更长）；若涉及开发者账号级处罚才走申诉流程。

## 🎨 最佳实践

先在内部测试渠道走通安装、更新、登录与数据迁移，再决定放量方式。发布包的应用标识要在早期确定；版本日志说明用户能观察到的改变，权限与 SDK 数据收集要和申报内容一致。

灰度能限制部分风险暴露，但不等于可自动回滚已安装的客户端。记录何种指标触发暂停，以及如何发布兼容旧数据的修复版；比例和观察时长根据风险与样本量选择。商店要求以提交时官方政策为准，不能靠一套固定流程保证通过。

## 练习与验收：内部测试轨道的交付验收

使用测试版本递增 versionCode，生成与发布配置对应的 AAB，通过内部测试轨道或适合该产物的测试流程安装。预期商店交付后的包能登录、访问测试数据并处理权限拒绝。再从旧测试版本升级，确认本地数据库和偏好保留。验收记录签名身份、版本号及升级数据；AAB 文件生成成功不等于某台设备能直接安装它。

以上是在个人或隔离测试环境中的练习，不是本轮已执行记录；实际运行范围见仓库文档质量报告。
