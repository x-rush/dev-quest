# Next.js 性能测试：从可重复实验到真实用户数据

> **阅读准备**：已有可稳定复现的页面与操作路径，理解发布构建、网络请求与浏览器主线程；先记录测试设备和数据规模。

本文面向能运行 React 页面、知道 HTTP 请求含义的读者。先完成一次生产构建，再学习采集指标，最后判断一次修改是否确实改善体验。需要 Node.js、项目锁文件、Chrome；负载实验另外需要 k6。

## 1. 先明确你要回答的问题

| 问题 | 方法 | 不能据此得出的结论 |
|---|---|---|
| 同一设备上，首屏改动是否变快？ | Lighthouse、DevTools，多次相同条件实验 | 所有真实用户都变快 |
| 移动端访客实际体验如何？ | 真实用户监控（RUM），按页面和设备分组 | 慢的原因一定是服务器 |
| 同时请求增加时，接口是否超时？ | k6 HTTP 负载实验 | 浏览器交互不卡顿 |
| 点击筛选后为什么停顿？ | DevTools Performance 录制交互 | 单靠请求时间可以定位主线程问题 |

实验先固定页面、数据量、构建版本和硬件。不要把开发模式与生产模式混在同一对比中；编译、开发检查和热更新会改变耗时。

## 2. 理解指标的单位和采集条件

LCP 衡量主要内容显示的时间，INP 衡量交互响应，CLS 衡量意外布局移动。当前良好阈值分别为 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1。真实用户评估应分设备看第 75 百分位，不能用三项平均分掩盖某一项不达标。FID 是旧指标，已由 INP 替代。[指标定义与评估方法](https://web.dev/articles/vitals)

没有交互的访问可能没有 INP 数据。“未采集到”应记为缺失，不能填 0。普通 Lighthouse 导航审计不直接测量真实用户 INP；TBT 可以帮助定位阻塞问题，但不能改名为 INP。

百分位需要一组样本。例如 100 次访问按耗时从小到大排序，p75 描述靠近第 75 个位置的体验。不同统计工具的插值算法可能略有差异，因此同一报表应固定算法、时间窗口和样本过滤规则。

## 3. 建立生产构建基线

在已有 Next.js 项目中执行：

```sh
npm ci
npm run build
npm run start
```

这些命令假设 package.json 的 build/start 分别执行 next build/next start。若采用静态导出或其他部署适配器，应使用其实际预览流程。另开终端或浏览器访问本地服务。

第一次实验记录：提交标识、Node 版本、浏览器版本、测试 URL、视口、网络和 CPU 限速、缓存状态。冷缓存与热缓存是两种实验，分别记录。首次请求还可能受到服务器懒初始化影响。

在 Chrome Lighthouse 面板选择相同设备配置，连续测试至少 3 次，保存报告并比较中位数。三次只是练习起点；如果波动明显，应增加次数并查找背景任务或不稳定网络。不要只保留最好的一次。

## 4. 在 Next.js 页面记录真实 Web Vitals

Next.js 提供 useReportWebVitals。以下组件只把数据写入控制台，适合本地理解回调；它不包含接收服务、持久化和聚合统计。

```tsx
// app/vitals.tsx
'use client';

import { useReportWebVitals } from 'next/web-vitals';

type Report = Parameters<typeof useReportWebVitals>[0];

const report: Report = ({ id, name, value, rating }) => {
  console.log('web-vital', { id, name, value, rating });
};

export function Vitals() {
  useReportWebVitals(report);
  return null;
}
```

在根布局的 body 中挂载一次 `<Vitals />`，并从 `./vitals` 导入。保持回调引用稳定，避免每次渲染创建新的报告函数。[Next.js 官方性能测量接口](https://nextjs.org/docs/app/api-reference/functions/use-report-web-vitals)

验证时先加载页面，再点击按钮、输入文字，最后切换到其他标签页，并启用控制台保留日志。部分指标在页面隐藏时报告；不要假设一挂载就出现完整三项结果。浏览器能力与访问行为也会影响可用数据。

接入实际监控时，只发送需要的字段，使用指标 id 识别更新，明确最后值与增量的处理方式。不要把带令牌的完整 URL、输入内容或用户个人信息塞入指标标签。上报失败不能阻塞业务操作。底层库的回调与上报说明见 [web-vitals](https://github.com/GoogleChrome/web-vitals)。

## 5. 用一次交互录制定位原因

选择明确动作，例如“在包含 1000 条商品的列表里输入搜索词”。打开 DevTools Performance 开始录制，执行该动作，停止后查看主线程：

1. 事件回调是否做了大规模同步计算？找耗时函数和长任务。
2. 是否反复触发布局？检查读尺寸与写样式是否交错。
3. 网络响应已到，但页面迟迟不更新？检查渲染工作和主线程占用。
4. 是否加载了与当前页面无关的大模块？结合构建输出和网络资源检查。

每次只改变一个主要因素，例如把重复过滤移出重复渲染路径。再次录制同一动作，比较任务时长与可见响应。不能仅因为用了 memo 或异步函数就宣称优化成功：async 函数里的同步计算仍可能阻塞线程。

## 6. 用 k6 验证服务端请求

k6 是独立运行时，不能用安装同名 npm 包替代。按 [官方安装步骤](https://grafana.com/docs/k6/latest/set-up/install-k6/)安装后，运行 `k6 version` 检查命令。以下文件只对你本机的应用执行小规模实验。

```js
// load.js，由 k6 执行，不是 node load.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 2,
  duration: '10s',
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
    checks: ['rate>0.99'],
  },
};

export default function () {
  const response = http.get('http://localhost:3000/');
  check(response, { '首页返回 200': (r) => r.status === 200 });
  sleep(1);
}
```

```sh
k6 run load.js
```

2 个虚拟用户各自循环执行请求与等待，并不意味着每秒恰好 2 次请求。这里 p95 < 500ms 和失败率 < 1% 是练习门槛，需要按业务目标调整；小样本短实验不能证明生产容量。

HTTP 请求不会执行 React，也不会绘制页面。首页响应快但客户端计算慢时，k6 结果可能很好而交互体验仍差。接口实验还要检查响应内容是否正确，避免把快速返回的错误页算作成功。

## 7. 报告应该包含什么

| 项目 | 应填写的实际信息 |
|---|---|
| 修改内容 | 例如为首屏图片提供合适尺寸；关联提交 |
| 固定条件 | 设备、浏览器、网络、CPU、数据、缓存状态 |
| 样本 | 实验次数或真实访问数量、采集时间窗口 |
| 修改前后 | 指标原始值、单位、选用的统计量 |
| 功能检查 | 图片是否完整，按钮行为是否仍正确 |
| 限制 | 本地结果；尚未覆盖低端设备或真实用户 |

不要用 Math.random 生成性能值，也不要在没有保存报告时写“实测提升 60%”。缺少基线就无法知道变化；有基线但条件不同，也不足以归因于代码修改。

## 8. 分阶段练习与验收

**第一阶段：采集。** 完成生产构建并保存三份同条件 Lighthouse 报告。验收：另一位读者能照着你的环境记录重做实验，并知道你比较的是中位数而非单次最好值。

**第二阶段：解释。** 找到一个尺寸未预留的图片区域，记录加载前后的布局变化，再为它提供正确宽高或宽高比。验收：解释空间为何被预留，并保存修改前后的录制；不能仅贴一个分数。

**第三阶段：扩展。** 在本地列表页面加入足够数据，录制一次筛选操作，再减少重复计算。验收：能指出具体耗时函数，并确认筛选结果未改变。如果测量没有改善，如实记录并解释下一步假设。

自测：k6 p95 达标能证明 INP 达标吗？不能，两者测量层次不同。未报告 INP 是否等于零延迟？不是。连续三次实验差距很大时，应该先宣布优化成功吗？应该先查实验条件与噪声。

本章提供可复现的操作方法，未声称已对某个业务站点完成性能实测。
