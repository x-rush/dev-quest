# 应用扩展：从单实例到多实例的具体问题

先修：HTTP 请求、数据库连接、缓存与部署。扩展的起点是某项容量或可靠性需求，例如“活动期间请求增加后 p95 超过目标”。单体应用也可以水平扩展，微服务不是必经阶段，分布式系统也没有无限容量。

## 1. 先找被耗尽的资源

| 证据 | 可能的瓶颈 | 首先验证 |
|---|---|---|
| CPU 持续忙，数据库响应正常 | 序列化、压缩、渲染或业务计算 | CPU profile 中的耗时路径 |
| 请求等待连接，数据库连接数接近上限 | 池太多、慢查询、长事务 | 活跃连接、等待时间、查询计划 |
| 内存随运行时间持续增长 | 无界缓存或泄漏 | 堆快照与对象保留路径 |
| 某地区慢、服务器处理时间短 | 网络距离或资源分发 | 分地区延迟和资源瀑布 |

增加实例只能缓解能分散到多个实例的负载。如果所有实例争抢同一数据库锁，扩容可能让排队更严重。

## 2. 垂直与水平扩展

垂直扩展是给一个实例更多 CPU 或内存，迁移成本通常较低，但仍有单实例容量和故障边界。水平扩展是在负载均衡后运行多个实例，要求请求不能依赖某一台机器独有的业务状态。

```text
浏览器 → 负载均衡 → Next.js 实例 A ─┐
                    Next.js 实例 B ─┼→ 数据库
                                   └→ 共享会话/对象存储/任务队列
```

本地 Map 里的登录会话、内存购物车和上传到实例磁盘的文件，会在请求落到另一实例时丢失。把必要状态放入共享存储；粘性会话能减少切换，但不能解决实例故障后的恢复。

## 3. 连接池预算：乘法比单个配置更重要

假设数据库总连接预算为 100，保留 20 给维护与其他服务，每实例池上限为 10，则应用最多 8 个实例就可能用完剩余预算：`8 × 10 = 80`。这是估算上限，不代表每个池始终占满。

无服务器并发、滚动发布中新旧版本共存、后台任务都可能增加实际连接数。先记录最大实例数与每实例池大小，再考虑代理、连接复用和查询优化。不能在每次请求中无条件创建一套全新连接池。

## 4. Next.js 多实例的额外边界

同一发布应让实例运行一致构建产物，并协调缓存与失效。某个实例内的缓存更新，不会天然通知另一台机器。自托管时根据部署方式配置缓存处理器；不要假设挂一个共享目录就覆盖所有缓存一致性问题。

滚动更新时，客户端可能还持有旧页面和旧 Server Action 引用。需要规划版本共存、部署标识、密钥一致性和请求落点。相关配置按实际 Next.js 版本与平台适配，详见[自托管文档](https://nextjs.org/docs/app/guides/self-hosting)。

反向代理要正确转发必要请求信息并支持预期的流式响应。健康检查应区分“进程存活”和“能处理业务”；数据库短暂异常时，让所有实例同时无限重启通常只会加重故障。

## 5. 长任务从请求中拆出

导出十万条记录或生成视频可能超过请求时限。可以让请求创建任务并返回任务 ID，Worker 从队列执行，页面查询状态或接收完成通知。

队列通常需要面对重试和重复交付。以导出为例，使用稳定任务 ID，记录状态转换，重复执行时复用已有产物或安全覆盖；不要把“消息只消费一次”当作天然保证。支付等外部副作用还需要对方的幂等能力与业务状态约束。

## 6. 什么时候拆服务

当某个业务能力有明确独立扩缩容、发布、权限或团队边界时，才评估拆分。代价包括跨服务调用失败、数据一致性、契约版本、追踪和运维。团队人数不能直接代入公式算出架构成本，也不能自动决定应从单体升级到微服务。

先在代码内分离模块、明确输入输出与数据库所有权；若这些边界尚不清楚，网络拆分通常会把耦合变成远程耦合。

## 7. 项目练习与验收

在本地以两个端口启动相同应用，用反向代理轮流转发。先做一个仅存在进程内的计数接口，观察结果可能交替；再把计数移到共享存储，解释一致性从哪里来。实验数据不能用作财务计数。

第二步停止一个实例，记录健康检查发现时间和失败请求。第三步模拟滚动升级，确认旧页面还能完成关键操作。验收材料包括架构图、连接预算、故障记录与回退步骤，而不是“支持水平扩展”的一句结论。

自测：增加实例一定减轻数据库压力吗？不一定。共享 Redis 就等于所有状态一致吗？不等于，还要看键、失效和事务。微服务天然比单体可扩展吗？不能脱离具体瓶颈判断。
