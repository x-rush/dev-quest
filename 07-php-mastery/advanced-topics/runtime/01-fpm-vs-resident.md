## 🔍 核心概念

### 概念一：FPM——每请求一次完整生命周期的"进程池"模型

**定义**: PHP-FPM（FastCGI Process Manager）维护一组常驻 worker 进程，但每个 worker 处理完**一个请求**后立即销毁本次执行的全部应用状态，再回到空闲队列。进程常驻，**应用不常驻**。

**请求生命周期**：

```text
浏览器请求 → Nginx → FastCGI → 空闲 worker 进程接管
  → 每请求重新初始化：加载框架 → 构建容器 → 中间件管道 → 控制器 → 响应
  → 请求结束，销毁本次请求的变量与框架对象；持久连接等由扩展或 worker 配置管理，不能假定它们一定关闭
  → worker 回到空闲，等待下一个请求
```

**关键特性**:

- **请求态默认重建**：普通 PHP 变量、静态属性和框架容器会在下一次请求重新建立；但持久连接、扩展全局状态和 worker 级缓存是例外，不能把它们当作请求隔离的证据
- **内存需要观测**：请求结束会释放请求使用的 zval 和对象；FPM worker 的进程与分配器仍常驻，扩展泄漏、持久缓存或高水位内存仍可能累积，应按 `pm.max_requests`、进程 RSS 和错误日志制定回收策略
- **发布即生效**：新代码下一次请求直接生效（OPcache 关闭时间戳校验时需 reload FPM）
- **OPcache 的角色**：消除"编译"成本（字节码常驻共享内存），但**框架启动逻辑照跑**——容器构建、配置加载、自动加载查找每请求重来

### 概念二：常驻内存——一次加载、服务成千上万次请求

**定义**: 进程启动时加载一次框架并常驻运行，之后每个请求只是"处理一个事件"，应用状态跨请求存活。Swoole、Workerman、RoadRunner、FrankenPHP 都属于这一模型。

```text
启动时：加载框架 → 构建容器 → 建立 Worker 进程 → 进入事件循环
每个请求：直接在已就绪的应用内处理（无框架启动税）
```

**收益来源**:

| 收益 | 来源 |
|------|------|
| 去掉启动税 | 框架初始化成本摊销到进程整个生命周期 |
| 可复用连接 | 长驻进程可管理连接复用；池大小、归还、事务回滚和数据库连接上限必须一起设计 |
| 进程内缓存 | 热数据放进程内，省一次网络往返 |
| 协程并发 | 受支持的 I/O 等待可让出执行权；可承载连接数取决于内存、限流、下游连接上限和实测负载 |
| 长连接能力 | WebSocket、TCP 服务、消息推送天然可行 |

### 概念三：状态泄漏——常驻世界的头号风险

常驻之后，"请求结束自动清场"的保证消失了。FPM 下无害的写法，在常驻环境里都是事故源：

| 写法 | FPM 下的表现 | 常驻下的表现 |
|------|-------------|-------------|
| 静态属性累积计数/缓存 | 每请求归零，无所谓 | 跨请求累积，成为隐藏全局状态 |
| 单例持有请求态（当前用户、租户 ID） | 天然每请求重建 | 第二个请求读到第一个请求的用户——**串户** |
| 容器外 `static` 局部变量缓存 | 生命周期=请求 | 生命周期=进程，失效时机难以推理 |
| 微小的内存增长 | 随进程销毁，无从察觉 | 数小时后 OOM，且难以复现定位 |

Laravel Octane 的官方文档专门列出了"容器注入、单例污染"的升级注意事项——那份清单本质上就是**常驻化代价清单**。

## 🛠️ 实践指南

### 步骤一：测量你的真实瓶颈

**目标**: 确认启动税是否真的是你的性能问题。

**操作指南**:

1. 用 Xdebug profile 或 Blackfire 分析一个典型请求，区分"框架启动"与"业务执行（DB/HTTP I/O）"耗时占比
2. 压测 P95/P99：若延迟主要来自 DB 查询与外部 API，先做索引与缓存（见[查询优化](../performance/01-query-optimization.md)、[缓存策略](../performance/02-caching-queues.md)）
3. 检查并发模型：FPM 的并发上限 = `pm.max_children`；I/O 等待期间进程被占满即排队，这才是"该换模型"的经典信号

**验证方法**: 能说清"我的 P95 花在哪、并发瓶颈是 CPU 还是 I/O 等待"。

### 步骤二：用常驻视角审计现有代码

**目标**: 评估一段 Laravel 代码常驻化时要改什么。

**操作指南**:

1. 全局搜索 `static` 属性与 `static` 局部变量：是否携带请求态？是否只增不减？
2. 检查 singleton 绑定：`AppServiceProvider` 中 `singleton()` 的类是否在构造器/属性里存了 `$request`、当前用户、租户上下文（应改为 `scoped`——每请求重建的"请求内单例"）
3. 检查 `.env`/配置读取时机：常驻下配置只在启动时加载一次，运行期改动不会生效
4. 检查全局文件句柄、外部连接：异常路径上是否会泄漏

**验证方法**: 输出一份"常驻化改造清单"，每条对应一处具体代码。

## 💻 代码示例

### 示例：FPM 无害、常驻危险的代码

```php
<?php

declare(strict_types=1);

final class TenantContext
{
    private static ?int $tenantId = null;   // ⚠️ FPM：每请求归零，无害
                                            // ⚠️ 常驻：跨请求存活，A 公司请求后
                                            //     B 公司请求可能读到 A 的租户 ID

    public static function set(int $tenantId): void
    {
        self::$tenantId = $tenantId;
    }

    public static function get(): ?int
    {
        return self::$tenantId;
    }
}
```

**关键点解析**:

- 问题不在"静态变量"本身，而在**生命周期假设**：这段代码默认"每个请求从零开始"
- 常驻化的正确姿势是**请求作用域上下文**：Laravel 里用 `scoped()` 绑定，Webman/Swoole 里用协程上下文或显式参数传递
- 反过来，跨请求**无请求态**的静态缓存（如只读配置、路由表）在常驻下反而是巨大收益

## 🎨 最佳实践

FPM 的请求生命周期比较明确，常驻进程则把启动成本分摊到多次请求，同时要求重新审视状态与资源。若瓶颈是慢 SQL，换运行模型不会自动修复查询；先从 profile 确认收益，不用没有证据的“99.9% 场景”作选型结论。

迁移前列出静态属性、单例、用户身份和数据库连接由谁持有，验证前一个请求结束后不会影响下一个。用连续负载观察内存、延迟与连接恢复；长连接或后台任务需求也可能是采用常驻模型的理由。框架与运行时并非同一层，适配关系要按具体组合判断。

## ❓ 常见问题

### Q1: OPcache 已经常驻了字节码，为什么还说 FPM 每请求有启动成本？

**A**: OPcache 缓存的是**编译产物**（opcode），省掉的是"读取源文件 + 词法语法分析 + 编译"。但每请求仍要执行框架的**初始化逻辑**：实例化容器、注册服务、解析路由表、加载配置。这部分在 Laravel 里是几毫秒到几十毫秒的纯执行成本，OPcache 帮不上忙。

### Q2: 那我该学 Swoole 还是 Workerman/Webman？

**A**: 这两派后续两篇专题展开：[Workerman 原理](./02-workerman-principles.md)与[Webman 实战](./03-webman-practice.md)是"多进程 + 事件循环"路线（纯 PHP、部署简单）；[Swoole 协程生态](./04-swoole-ecosystem.md)是"C 扩展 + 协程"路线（并发原语更强、生态组件多）。

## 📝 总结

### 核心要点回顾

1. **FPM = 进程常驻、应用每请求重建**：用启动成本换"干净世界"的安全保证
2. **常驻 = 应用跨请求存活**：省启动税、连接池、协程并发，代价是状态泄漏风险内化到代码层
3. **两者是运行模型的分岔，不是新旧替代**：按 I/O 形态与团队约束选型
